# Журнал изменений

## Регистрация и авторизация пользователей (роли «администратор» и «просмотр»)

Склад закрыт от неавторизованного доступа: вход по логину и паролю, сессия
в HttpOnly-cookie до выхода пользователя, две роли с проверкой прав на
серверной стороне. Формат трёх основных листов файла данных не меняется.

### Структура и данные

- **Новые листы** (создаются лениво, как корзина и категории; их можно
  удалить в Excel — пересоздадутся):
  - **«Пользователи»**: `ID | Логин | Хеш_Пароля | Роль | Создан | Заблокирован`
    («Роль» — «администратор»/«просмотр», «Заблокирован» — отметка времени
    блокировки или пустая строка);
  - **«Сессии»**: `Токен | ID_Пользователя | Создан` — токен-cookie →
    пользователь, живёт до выхода (logout) или удаления учётной записи.
- **Пароли** — PBKDF2-HMAC-SHA256, 600 000 итераций, случайная соль
  (`domain/passwords.py`, только стандартная библиотека; формат строки
  самоописывающий: `pbkdf2_sha256$итерации$соль$хеш` — старые хеши
  проверяются, новые пишутся сильнее). Хеши никогда не покидают backend:
  в ответах API и на листе «Пользователи» хранится только хеш.
- **Роли**: на листе — по-русски («администратор»/«просмотр»), на границе
  API — слаги `admin`/`viewer` (`domain/users.py`). «Просмотр» может только
  читать данные склада; мутации и управление пользователями — только
  администратор.

### Разграничение доступа (на сервере, а не только в интерфейсе)

- **`app/api/deps.py`**: зависимости `get_current_user`/`require_auth`
  (cookie → сессия → учётная запись, иначе 401) и `require_admin`
  (иначе 403).
- Все данные склада требуют входа: `/api/stats`, списки и детали мест,
  ящиков, вещей, поиск, категории, корзина, QR-коды — 401 без валидной
  сессии. Открыты только `GET /api/health` и `/api/auth/*`.
- **Все мутации** (создание/правка/удаление мест, ящиков, вещей, категорий,
  восстановление и очистка корзины, backup, сброс кэша) — только роль
  «администратор» (403 остальным).
- **`AuthError` → 401 и `ForbiddenError` → 403** в `domain/errors.py`
  (хендлеры в `create_app`); новые листы в `storage/schema.py`; методы
  пользователей/сессий в `ExcelRepository` (RLock, атомарная запись),
  Protocol и `CachedRepository` (мимо кэша — проверка доступа обязана
  видеть актуальные блокировки); сценарии — новый `services/auth_service.py`
  и синглтон `get_auth_service()` в `context.py`.

### API

- **`/api/auth/*`**: `POST /api/auth/register` — самостоятельная регистрация
  (роль «просмотр»; **самая первая учётная запись на пустом складе получает
  «администратора»** — bootstrap, иначе администратора некем создать),
  `POST /api/auth/login`, `POST /api/auth/logout` (204, сессия удаляется на
  сервере), `GET /api/auth/me`. Cookie `storage_session`: HttpOnly,
  SameSite=Lax, 30 дней (серверная сессия — до выхода).
- **`/api/users`** (только администратор): `GET` — список; `POST` — создать
  с любой ролью; `PATCH /{id}` — логин, пароль (пустой — не менять), роль,
  блокировка; `DELETE /{id}` — удалить вместе с сессиями.
- **Ошибки-контракты**: неверный логин или пароль, заблокированная учётная
  запись — 401; занятый логин — 409; неизвестная роль, плохой логин/пароль —
  400; неизвестный пользователь — 404. Защита от потери доступа: нельзя
  понизить, заблокировать или удалить последнего действующего администратора
  (400).

### Интерфейс

- **`auth.tsx`** — контекст авторизации: при монтировании `GET /api/auth/me`,
  login/register/logout; любой 401 вне `/api/auth/*` сбрасывает пользователя.
- **`pages/Login.tsx`** (`/login`, вне Layout) — вход и регистрация
  переключателем, ошибки API — как есть, после входа возврат на исходную
  страницу (`state.from`).
- **`RequireAuth`/`RequireAdmin`** в `App.tsx`: неавторизованные →
  `/login`, роль «просмотр» уводится с `/add`, `/settings`, `/users`.
- **`pages/Users.tsx`** (`/users`, админ) — таблица учётных записей:
  создание (логин, пароль, роль), редактирование (логин, сброс пароля,
  роль, блокировка), удаление с confirm.
- **`Layout.tsx`** — блок пользователя в sidebar (логин, роль, «🚪 Выйти»);
  для «просмотра» скрыты «＋ Добавить», ⚙, «Резервная копия» и админские
  кнопки на страницах (создание ящиков/мест, правка, степпер/перенос,
  bulk-таблица, восстановление/очистка корзины); проверка прав при этом
  всегда выполняется сервером.
- `api.ts` — все запросы с `credentials: "include"`, типы User и API
  авторизации/пользователей.

### Тесты

- Новый `tests/test_api_auth.py` (16): bootstrap первой учётной записи,
  роль «просмотр» у остальных, дубликат логина 409, валидация входа,
  вход/выход/me, 401 без сессии, «просмотр» читает но не пишет (14 мутаций
  → 403), управление пользователями, сброс пароля, защита последнего
  администратора, блокировка (вход и сессия), очистка сессий при удалении.
- Фикстура `client` в `conftest.py` — залогиненный администратор с
  фиксированной сессией; генераторы фикстур переносят листы
  «Пользователи»/«Сессии» при перезаписи файла. Итог: **248 тестов,
  все зелёные**.

## Страница настроек: справочник категорий

В шапке (правый верхний угол) появилась кнопка ⚙ — она ведёт на отдельную
страницу настроек `/settings` со справочником категорий: добавление,
переименование и удаление. Страница построена секциями (оверлайн + карточка),
чтобы в будущем добавлять туда новые настройки.

### Структура и данные

- **Новый лист «Категории»** (один столбец «Название») — справочник «впрок»,
  создаётся лениво, при первой категории, добавленной в настройках (как и
  корзина). Три основных листа не меняются, старые файлы открываются как
  раньше; лист можно удалить в Excel — он пересоздастся.
- Общий список категорий (`GET /api/categories`) теперь — объединение
  справочника и категорий, используемых у вещей (без учёта регистра, по
  алфавиту): категорию можно завести заранее, без единой вещи.
- **Мутации** (правят справочник и вещи за одно сохранение файла):
  `POST /api/categories` — добавить (дубликат без учёта регистра → 409);
  `PATCH /api/categories` (`{name, new_name}`) — переименовать у всех вещей,
  смена только регистра легальна; `DELETE /api/categories?name=` — удалить,
  вещи становятся «без категории». Ответ — `{name, items_updated}`.
  Категория адресуется телом/параметром, а не путём: названия могут
  содержать «/». Колонка «Обновлён» у вещей при этом не трогается.
- Слои: `domain/categories.py` (`combined_categories`, `find_category`,
  `validate_category_name`), `storage/excel_repository.py` (лист «Категории»
  + три мутации), сервис и кэш дополнены методами категорий; роутер
  `api/routes/categories.py`, GET переехал из роутера вещей.
- Тесты: `test_api_categories.py` (20 шт.) — справочник, дубликаты, нормализация,
  регистровое переименование, очистка вещей, ленивое создание листа.

### Интерфейс

- **`pages/Settings.tsx`** — страница `/settings` (кнопка ⚙ в шапке —
  `NavLink` с активным состоянием): поле добавления, список категорий со
  счётчиком вещей у каждой, инлайн-переименование (Enter/Escape), удаление
  через confirm с предупреждением «N вещей станут "без категории"».
  Новые разделы настроек добавляются по той же схеме: оверлайн + Card.
- Маршрут `/settings` в `App.tsx` (10 страниц). Список и счётчики
  перечитываются после мутаций автоматически (глобальная версия данных).

## Полный React-интерфейс (итерация 3)

Фронтенд превращён из одноэкранной сводки в полноценное приложение поверх
REST API итерации 2: 9 страниц с роутингом, обе темы, bulk-редактор таблицы
вещей, полоса отмены удалений. Формат файла данных не менялся; backend
дополнен двумя эндпоинтами — `PATCH /api/boxes/{id}` и
`PATCH /api/locations/{id}` (частичное обновление ящиков и мест, см.
«Редактирование ящиков и мест» ниже). Единственная новая фронтенд-
зависимость — `react-router-dom` (принцип минимализма: без UI-китов,
react-query и иконок).

### Структура и данные

- **Роутер**: `BrowserRouter` + `<Routes>`; маршруты `/`, `/boxes`,
  `/box?box={id}` (формат QR-ссылок API), `/items`, `/item/{id}`, `/add`,
  `/locations`, `/trash`, `/search?q=`. `/box` без параметра перенаправляет
  на `/boxes`; неизвестный путь — на обзор. Deep links работают через
  SPA-fallback Vite.
- **`api.ts`** — тонкий REST-клиент: типы повторяют Out-схемы бэкенда
  (snake_case), `request()` разбирает `{"detail": "текст"}` и показывает
  текст как есть (пользовательский контракт); сетевой сбой даёт понятное
  «Нет связи с API…». Дата-хелпер приводит `YYYY-MM-DD HH:MM:SS` к
  `DD.MM.YYYY HH:MM`.
- **Хук `useApi`** (без react-query): loading/error/refetch + глобальная
  «версия данных» — после любой мутации все смонтированные чтения
  перечитываются (backend и так сбрасывает свой кэш после каждой записи).
- **Провайдеры** (`components/ui.tsx`): тосты (успех/ошибка), полоса отмены
  «Только что удалено: … [Отменить]» с таймером ~30 с и восстановлением по
  одной записи (итог — «Восстановлено: N, пропущено: M»).

### Страницы

- **Обзор** — bento-плитки («единиц на складе» + ящики/вещи/места) и
  «недавно обновлённое» (top 5 по `updated_at`), CTA «Добавить вещь».
- **Ящики** — карточки с «ед. · поз.» и местом; создание модалкой; дубль
  имён ящиков в селектах подписывается суффиксом « · #xxxx» (только
  отображение).
- **Ящик** — инфо, QR (`<img src=…/qr>`, клик — оверлей с blur, закрытие по
  Esc/фону), редактирование (название, место, описание — см.
  «Редактирование ящиков и мест» ниже), содержимое карточками, удаление с
  confirm и отменой.
- **Вещи** — фильтры чипами (ящик/категория), переключатель
  «Карточки ⇄ Таблица» (выбор запоминается).
- **Таблица вещей** — bulk-редактор: чекбоксы с indeterminate-заголовком,
  инлайн-правка (название/ящик/количество/категория/заметки), «добавить
  строку», подсветка изменённых (индиго) и новых (зелёный) строк, счётчик
  несохранённых правок, «Отмена» с confirm при правках, сохранение через
  `PUT /api/items` и массовое удаление через `DELETE ?ids=`. Таблица всегда
  работает со всем листом (bulk-save перезаписывает его целиком), поэтому
  при активных фильтрах показывается подсказка.
- **Вещь** — степпер количества (минус выключен на нуле; PATCH допускает 0),
  перенос select'ом (`POST …/move`, «— без ящика —» через PATCH `box_id: ""`),
  редактирование модалкой, отправляющей **только изменённые поля** (каждое
  обновление ставит штамп «Обновлён» — лишних штампов нет), удаление с
  отменой.
- **Добавить вещь** — ящик, количество ≥ 1 (422-инвариант бэкенда
  отражён в валидации формы), пикер категории со «➕ Новая категория…» и
  resolve-логикой (регистровые дубли сводятся к каноническому написанию).
- **Места** — карточки со счётчиком ящиков; создание; редактирование
  (название, описание; 409 переименования в существующее место — inline);
  confirm удаления объясняет, что ящики останутся «без места хранения».
- **Корзина** — тип (вещь/ящик/место), название, происхождение («из ящика
  «X»», в том числе если родитель тоже в корзине), дата; «Восстановить» у
  каждой записи; очистка с двухшаговым подтверждением; `purged` — подписью
  в шапке.
- **Поиск** — глобальная строка в шапке; пустой запрос не отправляется
  (сервер на пустом `q` вернул бы все вещи); запрос приводится к нижнему
  регистру на клиенте (сервер сравнивает его с приведённым к нижнему
  регистру «стогом сена» — тесты бэкенда фиксируют этот контракт).

### Дизайн-система

- Токены обеих тем в `styles.css`: светлая (bg `#f4f4f6`, акцент
  `#4f46e5`) по умолчанию, тёмная (`bg #0E0F13`, индиго `#7D85EC`) по
  `[data-theme="dark"]` на `<html>`; выбор — в `localStorage` (`hs-theme`),
  применяется inline-скриптом в `index.html` до первой отрисовки (без
  вспышки светлой темы).
- Радиус 16 (карточки) / 12 (поля), две ступени теней + hairline-бордеры,
  h1 `clamp(1.6rem→2rem)/800/−0.03em`, caps-оверлайны, tabular-nums на всех
  числах, focus-ring на `:focus-visible`, явные `:disabled`,
  `prefers-reduced-motion` отключает анимации.
- Примитивы в `ui.tsx`: Card, Badge, Chip, Field, Modal (Esc/клик по фону),
  ConfirmDialog, EmptyState (CTA), ErrorState, Skeleton, Stepper,
  CategoryPicker.
- Адаптивность ≤ 640px: одна колонка, stats 2×2, sidebar → гамбургер
  slide-over с backdrop; сетки карточек `auto-fill, minmax(240px, 1fr)`.

### Редактирование ящиков и мест

Кнопки «✏️ Редактировать» на страницах ящика и мест: модалки с отправкой
PATCH только фактически изменённых полей, ошибки — inline, после сохранения
тост и авторефетч. Под ними — новые backend-эндпоинты (единственные
изменения backend в этой итерации):

- **`PATCH /api/boxes/{id}`** — частичное обновление ящика: `name`,
  `location_id` (пустая строка/NULL — «без места хранения», несуществующее
  место — 404 с текстом-контрактом `add_box`), `description`; лишние поля
  тела — 422 (`extra="forbid"`). Содержимое (вещи) не трогается — их
  подписи (`box_label`) обновляются автоматически, поскольку собираются при
  чтении. Ответ — свежая `BoxDetail` со счётчиками; кэш сбрасывается.
- **`PATCH /api/locations/{id}`** — частичное обновление места: `name`,
  `description`. Переименование в уже занятое имя (без учёта регистра) —
  409 с текстом-контрактом создания; своё текущее имя дубликатом не
  считается (инвариант проверяется в репозитории — там же, где и при
  `add_location`). Привязка ящиков не меняется: `box_count` в ответе
  актуален, `location_name` у ящиков обновляется сам.
- По слоям: `BoxUpdate`/`LocationUpdate` в `schemas.py`;
  `ExcelRepository.update_box`/`update_location` (зеркало `update_item`:
  проверка заголовков, `NotFoundError`, атомарная запись под RLock; у
  мест — проверка дубликатов имени); методы в Protocol
  `InventoryRepository` и проход в `CachedRepository`; валидация в
  `InventoryService` — названия через доменные модели `Box`/`Location`
  («Укажите название ящика/места хранения.»), существование места при
  переносе ящика — по списку мест.
- Фронтенд: `updateBox`/`updateLocation` в `api.ts`.
- Тесты: 7 новых в `test_api_boxes.py` (rename+описание, перенос и
  отсоединение места, 404 чужого места, 400 пустого названия, 404 ящика,
  422 лишнего поля, сохранность содержимого с обновлённой подписью) и
  7 новых в `test_api_locations.py` (rename+описание со счётчиком, 409
  дубликата, rename в себя, 400, 404, 422, сохранность привязки ящиков).

### Проверка

- `npm run build` (tsc strict + vite) — зелёный.
- Backend: **191 тест, все зелёные** (177 прежних + 7 на PATCH ящиков +
  7 на PATCH мест).
- Живой сценарий против dev-сервера (API на изолированном файле данных):
  место → дубликат 409 → ящик → QR (PNG, 404) → вещи → PATCH → move →
  detach → фильтры → поиск (по названию/подписи ящика) → категории →
  bulk PUT (включая новую строку и мусор в количестве → `to_qty`) →
  массовое удаление с дедупликацией → корзина → restore (включая
  перепривязку ящика при восстановлении места) → очистка → бэкап →
  редактирование ящика (rename, перенос места, отсоединение, 404/400/422,
  подписи вещей вслед за переименованием) → редактирование места
  (rename, 409 дубликата, rename в себя, 404/400/422, счётчик и
  `location_name` ящиков вслед за переименованием). SPA-fallback
  `/box?box=…`, CORS-preflight. 37/37 + 9/9 + 9/9 проверок.

## Полный CRUD REST API (итерация 2)

API доведён до полного набора операций: места хранения, ящики (включая
QR-коды), вещи (CRUD + bulk-операции), корзина, поиск, категории, резервная
копия. Формат файла данных не меняется; существующие `/api/health` и
`/api/stats` не тронуты — текущий фронтенд продолжает работать.

### API

- **Эндпоинты** (полная таблица — в README): CRUD `/api/locations`,
  `/api/boxes` (деталь с содержимым, QR `GET /api/boxes/{id}/qr`),
  `/api/items` (POST/PATCH/DELETE, `POST /api/items/{id}/move`, массовое
  `DELETE ?ids=`, bulk-save `PUT`), `/api/search?q=`, `/api/categories`,
  `/api/trash` (список с авто-очисткой просроченных, восстановление трёх
  типов, очистка), `POST /api/backup`, `POST /api/cache/clear`.
- **Статусы ошибок через подклассы**: в `domain/errors.py` добавлены
  `NotFoundError(StorageError)` → 404 и `ConflictError(StorageError)` → 409;
  `ValidationError` → 400, прочий `StorageError` → 503. В `create_app`
  регистрируются exception-хендлеры (Starlette ищет обработчик по MRO,
  порядок объявления не важен), ответ — `{"detail": str(exc)}`; try/except
  в роутерах не нужны. Тексты-контракты не изменились — подклассы меняют
  только тип исключения.
- **`routes.py` → пакет `routes/`** (health/locations/boxes/items/trash).
  `schemas.py` дополнен входными моделями (`extra="forbid"` — лишние поля
  тела запроса дают 422), фабриками «строка DataFrame → ответ» и слагами
  корзины item/box/location ↔ вещь/ящик/место; `data` записи корзины —
  сырой снапшот исходной строки с русскими ключами как есть.
- **PATCH-семантика вещей**: `box_id` обрабатывается как перенос
  (`move_item` с проверкой существования ящика; пустая строка/NULL —
  «без ящика»), остальные поля — точечное обновление; категория
  нормализуется к каноническому написанию справочника
  (`normalize_category` в роутере, как в прежнем UI). `quantity` — ge=1
  при создании, ge=0 при обновлении.
- **QR-коды**: ссылка `{base}/box?box={id}`, где base — `BASE_URL`, а без
  него — адрес запроса; PNG в память (`qrcode.make` → BytesIO). Зависимости
  `qrcode==8.0`, `pillow==11.1.0` вернулись в `requirements.txt`.
- После каждой записи роутер сбрасывает кэш чтений (`clear_cache()`), поэтому
  ответы всегда собираются из актуального файла, а не из 30-секундного кэша.

## Исправление логических ошибок + переработка UI

### Логика

- **Редактор таблицы «Вещи»** — три связанных исправления сохранения:
  - строки, добавленные прямо в таблице, больше не получают ID «nan»
    (NaN в пустых ячейках — truthy; теперь ячейки очищаются NaN-безопасным
    хелпером ``clean_text``/``clean_id``, пустой ID получает новый);
  - очищенная ячейка «Количество» (NaN) или текст из вручную правленого
    файла больше не роняет сохранение (безопасное приведение ``to_qty``,
    отрицательное клампится в 0);
  - отметка «Обновлён» проставляется только фактически изменённым и новым
    строкам — неизменённые больше не «обновляются» при каждом сохранении,
    и «Недавно обновлённое» на Обзоре снова имеет смысл (сравнение — чистая
    функция ``item_row_changed`` с нормализацией обеих сторон).
- **Дубликаты имён ящиков** теперь дают уникальные подписи в выпадающих
  списках (суффикс « · #xxxx» из последних символов ID): карта
  «подпись → ID» однозначна, вещь не уедет в другой ящик с тем же именем
  (``helpers.box_label_map``; формат файла не меняется).
- **Массовое удаление** (``ExcelRepository.delete_items``) — дубликаты ID во
  входном списке дедуплицируются: одна запись в корзине, никаких повторных
  ``delete_rows``, из-за которых сдвигались индексы и удалялась чужая строка.
- **Корзина** — повреждённая (пустая или без ID) JSON-запись больше не
  восстанавливается как пустая строка: ``StorageError «Запись корзины
  повреждена…»``, целевой лист не трогается.
- **Полоса отмены** — восстанавливает записи по одной; «не найдена в корзине»
  (уже восстановлено в другой вкладке) считается пропуском, а не сбоем;
  итог — тост «Восстановлено: N, пропущено: M».
- **Категории** — один механизм дедупа для всех: алгоритм перенесён в домен
  (``app/domain/categories.py``), ``InventoryService.get_categories`` и
  ``forms.category_options`` пользуются им вместе. «Инструменты» и
  «инструменты» — одна категория с каноническим первым написанием везде,
  включая таблицу «Вещи».
- **Кнопки «−/+»** — «−» при нуле отключена и не делает холостую запись
  с ложным тостом; на «Редактировать» то же самое, а «задать точное
  количество» без изменения значения больше не пишет файл.
- **Суммы количества** (Обзор, содержимое ящика, «Редактировать») — общий
  хелпер ``qty_total``: текст в «Количество» из вручную правленого файла
  больше не валит страницы с TypeError.
- **Глубокая ссылка** ``/?box=<id>`` с несуществующим/устаревшим ID больше не
  рисует пустую страницу — показывается обычный Обзор с разовым
  предупреждением (валидный ID по-прежнему перенаправляет на «Ящик»).
- **Защита от гонок кэша**: «Редактировать» и «Ящик» при исчезновении записи
  между чтением списка и рендером берут первую доступную запись вместо
  IndexError.
- **Запуск** — ``python C:\путь\main.py`` из другого каталога работает
  (в ``streamlit run`` передаётся абсолютный путь).
- **Docker** — у ``BASE_URL`` в docker-compose больше нет умолчания
  ``http://localhost:8501``: без явной настройки QR-коды строятся из адреса,
  под которым открыто приложение (телефон в той же сети), как и описано в
  README и ``qr.py``.

## Корзина: безопасное удаление с восстановлением

Раньше любое удаление (вещь, ящик, место) было немедленным и необратимым:
один случайный клик терял данные. Теперь удаление переносит запись в
корзину (как в Notion / Google Drive / Any.do), откуда её можно вернуть.

**Ключевые решения**

- *Хранение.* Четвёртый лист «Корзина» создаётся лениво, при первом
  удалении (тот же паттерн ``ensure_worksheet``, под тем же ``RLock``).
  Колонки: ``Тип | ID | Название | Данные | Родитель_ID | Дата удаления``.
  Исходные значения строки хранятся одним JSON-столбцом «Данные»: у трёх
  листов разные наборы колонок, а JSON сохраняет точные исходные значения
  без «супер-шапки». Три основных листа не меняются — старые файлы
  открываются без изменений и без миграции.
- *Каскады — отсоединение вместо удаления.* Ящик с вещами уезжает в
  корзину один, вещи остаются в «Вещях» с прежним ``Ящик_ID`` и
  отображаются как «— без ящика —»; место уезжает без ящиков, они
  показываются как «— без места хранения —». ID никогда не меняются и не
  перегенерируются, поэтому восстановление ящика/места автоматически
  возвращает привязки — отдельного «восстановления содержимого» не нужно.
  Прежние чекбоксы «Удалить вместе с содержимым»/«Подтверждаю удаление»
  и запрет удаления места с ящиками убраны как не нужные.
- *Механизм отмены — один на всё приложение.* У ``st.toast`` нет
  action-кнопок, поэтому «Отменить» живёт в компактной полосе «Только что
  удалено: … [Отменить]» вверху текущей страницы (``app/ui/trash.py``,
  рендерится из ``page_header``). Полоса исчезает при переходе на другую
  страницу, через 30 секунд или при новом удалении; отменяется всегда
  только последнее действие.

### Хранение

- ``app/domain/fields.py`` — ``TRASH_FIELDS``; ``app/storage/schema.py`` —
  лист ``SHEET_TRASH = "Корзина"`` и его шапка.
- ``app/domain/trash.py`` (новый) — константы типов (вещь/ящик/место),
  модель ``DeletedEntry``, кодирование строки в JSON и чистая логика
  истечения срока (30 дней), устойчивая к битым датам и битому JSON.
- ``ExcelRepository`` — методы корзины ``load_trash`` (не создаёт лист,
  если его нет), ``trash_add``, ``trash_restore`` (возвращает строку на
  исходный лист по её заголовкам, без смены ID), ``trash_clear``,
  ``trash_purge_expired``; ``delete_item`` / ``delete_box`` /
  ``delete_location`` и новый массовый ``delete_items`` теперь атомарно
  (один lock + одно сохранение, tmp + ``os.replace`` как прежде) переносят
  строку в корзину вместо физического удаления.

### Сервис

- ``InventoryRepository`` (Protocol) дополнен методами корзины;
  ``delete_box`` потерял параметр ``force``.
- ``CachedRepository`` кэширует и ``load_trash``; записи корзины идут мимо
  кэша, как остальные записи.
- ``InventoryService`` — ``delete_*`` возвращают ``DeletedEntry`` для
  полосы отмены; ``trash_entries`` (новее сверху), ``restore``,
  ``clear_trash``, ``purge_expired_trash`` (срок 30 дней —
  ``TRASH_RETENTION_DAYS``).

## Исправлено: QR-код ящика не показывался

Блок с QR-кодом на странице «Ящик» появлялся только если задана переменная
окружения ``BASE_URL``; без неё QR молча не рисовался.

- Если ``BASE_URL`` не задан, ссылка строится из адреса, под которым
  приложение открыто в браузере (заголовок ``Host`` текущего запроса): QR
  работает и с компьютера, и с телефона в той же сети без настройки.
  Явно заданный ``BASE_URL`` по-прежнему имеет приоритет (например,
  фиксированный адрес сервера в Docker).
- Блок QR сделан компактным и встроен в карточку ящика: клик по коду
  открывает увеличенную копию поверх страницы (клик по фону закрывает);
  отдельные кнопки и подписи убраны.

## Исправлено: новые категории не создавались из форм

Выбор «➕ Новая категория…» в формах «Добавить вещь» и «Изменить поля вещи»
не показывал поле ввода, и вещь сохранялась без категории. Причина: пикер
категории находился внутри ``st.form``, а виджеты внутри формы не вызывают
перезапуск скрипта до нажатия кнопки сабмита — условное поле ввода не
появлялось, а введённый текст терялся после сабмита с
``clear_on_submit=True``.

- **Формы** — пикер категории вынесен из ``st.form`` (рендерится рядом с
  формой как обычный виджет): выбор «➕ Новая категория…» моментально
  показывает поле ввода, итоговое имя вычисляется при сабмите через чистую
  функцию ``resolve_category`` (обрезка пробелов, пустое имя — явное
  предупреждение, вещь не сохраняется; совпадение с существующей категорией
  без учёта регистра сводится к её написанию).
- **Таблица «Вещи»** — колонка «Категория» снова допускает свободный ввод
  (``TextColumn`` вместо ``SelectboxColumn``); при сохранении значения
  нормализуются: пробелы обрезаются, регистровые дубли сводятся к
  каноническому написанию.
- Логика выбора категории вынесена в чистые функции ``resolve_category`` /
  ``normalize_category`` / ``category_options`` (модуль ``app/ui/forms.py``)
  и покрыта тестами ``tests/test_forms.py``.

## Категории — общий список для всех вещей

Раньше категория вещи была свободным текстом — один и тот же раздел
писался по-разному («Инструменты», «инструменты»). Теперь категории общие:

- **Формы «Добавить вещь» и «Редактировать»** — категория выбирается из
  выпадающего списка уже используемых категорий (одного и того же для всех
  вещей, по алфавиту) либо заводится новая через вариант «➕ Новая категория…».
- **Таблица «Вещи»** — колонка «Категория» тоже стала выбором из общего
  списка (существующие значения ничего не ломают — они входят в список).
- Формат файла данных не меняется: категории по-прежнему хранятся в колонке
  «Категория» листа «Вещи»; общий список складывается из того, что уже
  используется у вещей. Пока категорию использует хотя бы одна вещь — она
  видна в списке.

## Рефакторинг: слоистая архитектура (без изменения поведения)

Тот же стек (Streamlit + pandas + openpyxl), те же возможности и тот же
внешний вид. Данные — по-прежнему один файл Excel, старые `inventory.xlsx`
открываются без изменений.

### Что изменилось структурно

Было: один файл `app.py` (~1800 строк) — хранилище, домен, кэш, стили,
все страницы и точка входа в одном модуле.

Стало: пакет `app/` с явными слоями. Направление зависимостей:
`ui → services → domain ← storage`.

### Введённые швы (seams)

1. **`InventoryRepository`** (`app/services/repository.py`) — `typing.Protocol`:
   сервисы зависят от абстракции, конкретная реализация (`ExcelRepository`)
   подставляется в `app/context.py`. Никакого DI-фреймворка.
2. **`CachedRepository`** (`app/services/caching.py`) — декоратор-обёртка
   над портом: чтения кэшируются на 30 секунд (`st.cache_data`), записи идут
   напрямую; `clear_cache()` централизован.
3. **Доменные модели** (`app/domain/models.py`) — валидация входа сценариев
   (непустое название, целое неотрицательное количество) до записи в файл.

### Что сделано намеренно без изменений

- **Формат файла данных**: те же три листа («Места», «Ящики», «Вещи») с теми
  же колонками; всё, кроме «Количество», хранится строками; пустые ячейки
  при сохранении — `None`.
- **Миграция legacy-файлов** перенесена дословно, включая особенность
  порядка листов после миграции (`Ящики, Вещи, Места` — зафиксировано
  characterization-тестом как текущее поведение).
- **Атомарная запись** (tmp-файл + `os.replace`) и **threading.RLock**
  сохранены как есть — теперь это детали `ExcelRepository`.
- **Все тексты ошибок** (`StorageError`) — пользовательский контракт,
  формулировки совпадают дословно.
- **Кэш на 30 секунд**, кнопки «🔄 Обновить данные» и «💾 Резервная копия»,
  все русские подписи UI, темы, QR-коды, глубокие ссылки (`/box?box=`,
  `/?box=`) — без изменений.
- **Переменные окружения** `DATA_FILE`, `APP_TITLE`, `BASE_URL` — те же
  имена, умолчания и поведение (у `BASE_URL` обрезается хвостовой слэш).

### Запуск

- Было: `streamlit run app.py`
- Стало: `streamlit run main.py` (Dockerfile обновлён; docker-compose
  не требует изменений).

### Тесты

Новые: `tests/` — домен, миграция, хранилище (round-trip, атомарность,
ошибки, сбои I/O через monkeypatch), сервисы (сценарии, поиск, кэш),
конфигурация. Фикстуры xlsx генерируются программно. Покрытие:
domain 100%, services 100%, storage 98–99% (непокрыты только защитные
ветки обработки повреждённого tmp-файла). Перед рефакторингом поведение
монолита было зафиксировано characterization-тестами (18 шт.).
